# Fourfold: M11.1 Results — Several apps on one server

*Status: 2026-11-13, M11.1 built; exit criterion met on the test VPS: two apps (`test.miniscript.org`, `test2.miniscript.org`) behind `fourfold front` under systemd, each as its own OS user, and every cross-app access attempted as those users refused. Records what was built for several apps on one server, each isolated by OS user, the choices made, and how it was tested. No MS2 changes; several engine processes per app, and the load test, were dropped with the user ([future.md](future.md)).*

## Summary

| Question | Outcome |
|---|---|
| Several apps behind one port 443? | **Yes.** `fourfold front` ends TLS with a certificate per app (by SNI), and passes each request by its `Host` to the app's engine over a Unix socket. |
| Each app as its own OS user? | **Yes.** The engine runs as `ff-<name>`; `code/` and `private/config/` belong to the developer and are only readable by it; its data and state are its own; no other app's user can reach any of it, or its socket. |
| A dropbox the engine can't read or rewrite? | **Yes.** `fourfold dropbox-writer`, as `ff-<name>-log`, owns `dropbox/`; the engine can't open the folder, and sends its lines over a socket only it can reach. |
| Does the engine still know the visitor? | **Yes.** `front` sends `Forwarded`; the engine trusts it only because it arrived over its Unix socket. `req.ip`, rate limits and the per-visitor caps see the visitor. |
| Live updates through `front`? | **Yes**: server-sent events stream through, and end when either side goes. |
| Tied to systemd? | **No.** systemd units are the supported path (Debian, Ubuntu); the processes need only be started as the right users with the right sockets (documented). |

## What was built

- **`front`** (new component, `hosts/front/`): `FrontServer` holds an `HttpServer` with TLS (the M11 limits, per visitor), a `ServerTls` with each app's certificate, a `CertificateManager` per app with its own state folder (`<state>/apps/<name>/`, so each app has its own ACME account and no two managers share files), and a port 80 server answering every manager's challenges and redirecting the apps' own names. `Upstream` is one engine: HTTP/1.1 over its socket, one exchange per connection at a time, idle connections kept 20 s (under the engine's keep-alive), a 2-minute wait for the response's headers (504), 502 when the engine isn't there or answers garbage, one retry on a fresh connection when a kept one turns out dead. Responses with a length (up to 16 MB) are collected; anything else streams through the visitor's `StreamWriter`, with the engine's connection closed when the visitor goes (noticed on the next bytes, or within 15 s).
- **The request passed on:** hop-by-hop fields dropped (and those `Connection` names), the visitor's `Forwarded`, `X-Forwarded-*`, `X-Real-IP` and `Expect` dropped, `Forwarded: for=…;proto=https;host=…` added (IPv6 bracketed and quoted, IPv4-mapped shown as IPv4). HEAD is sent as GET, so the visitor's server, which leaves out the body, still sends the right `Content-Length`.
- **`dropboxwriter`** (new component): `DropboxClient`, a `DropboxSink` for the engine (blocking, with a 5 s timeout, from worker threads; reconnects once if the writer restarted), and `DropboxWriter`, on an event loop, appending through the same partition code as before (no links followed, no dot-names). A length-prefixed protocol: name and text in, status and message out; names up to 1 KB and writes up to 1 MB, more closes the connection.
- **`partition`**: `Dropbox` writes to its folder or to a `DropboxSink`; `AppFolder` leaves a `dropbox/` it may not open (EACCES) unopened, and `dropbox()` then says to use `--dropbox-socket`.
- **`platform`**: `listenUnix` (the socket file made with no access, then opened to the mode asked for; a stale socket replaced, anything else refused), `connectUnix` (EAGAIN, a full queue, is an error), `unixSocketPath`; a Unix peer's address is `kUnixPeer` ("unix"); `connectionsForOpenFiles` moved here from the CLI.
- **`httpserver`**: `listenUnix`; a Unix peer is exempt from the per-address caps.
- **`pipeline`**: `clientAddress` trusts a Unix peer as a proxy, with no `proxy.trust` needed.
- **`config`**: `loadFrontConfig` (`server.apps.<name>`: `domains`, `socket`, `certFile`, `keyFile`; `server.front`: `tls` as `config.tls` without files, `server` as `config.server`); `loadConfig` accepts `apps` and `front` in the same file, so one server config serves front and the engines' ceilings.
- **`cli`**: `fourfold front`, `fourfold dropbox-writer`; `serve --listen unix:PATH` and `--dropbox-socket` (also on `migrate` and `backup`); a socket from systemd that's a Unix socket means "behind front": a host name is required, and the startup notice drops the TLS and proxy warnings. `StopSignals` and the listen parsing moved to headers of their own, for the new commands.
- **Tools:** `tools/server/`: the systemd units (`fourfold-front`, and templates `fourfold-app@` and `fourfold-dropbox@`, each a socket and a service), `fourfold-add-app` (users, groups, ownership and modes, the server config entry, the units; idempotent, and without systemd it stops after the permissions), `deploy.sh` (from a workstation, over SSH), `isolation-test.sh` (the container test).

## Choices made here

- **Decided with the user** (milestones.md): systemd units as the supported path, with the processes themselves knowing nothing of systemd; `front` a mode of the one binary, and a pure router; the dropbox made append-only by a logger process; no multi-process engines and no load test.
- **The engine trusts its Unix socket's peer, not a list of addresses.** Who can connect is the socket's group, which only `front` is in. No configuration to forget, and nothing an outside address can claim.
- **`front` strips the visitor's forwarding headers** rather than appending to them: it faces the internet, so nothing before it is trusted, and the engine sees exactly one hop.
- **HTTP/1.1 to the engine, one exchange per connection.** The engine's own `HttpServer` already speaks it; no multiplexing to get wrong; a stream simply keeps its connection.
- **Collect, or stream.** Collecting keeps the visitor's keep-alive (and HTTP/2 framing) with a correct length; streaming is needed only for event streams and very large responses.
- **A certificate manager, and an ACME account, per app**, each in its own folder: managers share no files (the account key would otherwise be raced for), and an app's certificate trouble stays its own.
- **An unknown host gets a 421** (Misdirected Request), on 443 and on port 80, rather than another app's site.
- **Socket permissions do the isolation**, with systemd's `SocketUser`/`SocketGroup`/`SocketMode`: the engine's socket is `ff-<name>:fourfold-front 0660`; the writer's `ff-<name>-log:ff-<name> 0660`.
- **The app folder is `0751`**: the dropbox writer must pass through to `dropbox/`; every partition below has no access for others.
- **The writer appends by name, as the engine did** (the same checks and the same partition code), and answers each append, so `dropbox.write` still reports a failure to the script.
- **`front` reads the server config through a script host of its own**, gone before it serves: `front` runs no MiniScript afterwards.

## Tests

- `test_platform`: `listenUnix` (mode, the path, the peer name, a stale socket replaced, a file refused), `connectUnix` with nothing listening or too long a path.
- `test_partition`: a `Dropbox` over a sink; an `AppFolder` whose `dropbox/` can't be opened.
- `test_pipeline`: `clientAddress` from a Unix peer, with no `proxy.trust`: `Forwarded` IPv4 and IPv6, a forged hop skipped, none at all.
- `test_dropboxwriter` (new): appends through the writer, in order, into subfolders; names an engine couldn't name refused (`..`, empty, dot-names); an over-limit request refused and the connection closed; the client failing clearly with no writer, and reconnecting after a restart.
- `test_config`: `server.apps` and `server.front` read; the same file still giving an engine its ceilings; mistakes reported (no apps, bad names, a domain in two apps, a non-host, a relative path, a lone `certFile`, unknown keys, files in `server.front.tls`).
- `test_front` (new): the request passed on (fields dropped and added, HEAD as GET, `Forwarded` forms); `Upstream` against a fake engine on a Unix socket (the visitor in `Forwarded`, the peer `unix`, a connection kept and reused, headers passed back, an engine restart, not running: 502, too slow: 504, garbage: 502); a stream passed through as it comes, ended by the engine, and dropped when the visitor goes; `FrontServer` over TLS with two apps (each its certificate by SNI, each its engine, 421 for another name, port 80's redirect, shutdown closing the engines' connections); an app with no certifiable name refused.
- `test_fourfold`: end to end, `serve` on a Unix socket with its dropbox through a writer, behind `FrontServer` over TLS: the page, the engine's headers and `__Host-` cookie, `req.ip` the visitor's, the dropbox lines (and `print`) arriving through the writer, the engine log; the new commands' argument errors.
- Everything new also passes under ASan, and the whole suite passes in the static Linux build (Alpine, epoll).

## In a container, with real users

`tools/server/isolation-test.sh`: Debian 12, the static binary, two apps set up by `fourfold-add-app`, each process started by hand as its user (no systemd), front with its own certificates on 8443. **42 checks, all passed:** both apps answer through front with the visitor's address, an unknown name gets 421, port 80 redirects, a dropbox line arrives (`ff-a-log:ff-a-log 0640`); app `a`'s engine can't read `b`'s data, secrets, code, state or dropbox, nor connect to `b`'s engine or writer, nor write its own code or config, nor read, list, truncate or remove its own dropbox, nor read front's keys or change the server config, but can read its code and secrets and write its data and state; the writer can't read the app's data, secrets or code, nor reach its engine; front can't read any partition, nor reach a writer; the developer can edit code and config and read the dropbox and data, but not write the dropbox.

Found here: without systemd, the users must be able to make their sockets in `/run/fourfold/` (`1733`, now in the admin guide); systemd's socket units make them otherwise.

## On a public server

The M11 VPS (Vultr, 1 vCPU, 1 GB, Ubuntu 26.10), M11's single-app units removed, then `tools/server/deploy.sh` twice: `guestbook` (its data kept from M11) on `test.miniscript.org`, `newsfeed` (jobs and server-sent events) on `test2.miniscript.org`.

- **Certificates:** a real one from Let's Encrypt for each app, each within a second or two of front starting; restarting front for the second app reused the first's from disk.
- **Through front:** HTTP/2, the engines' headers and `__Host-` cookies; the engine logs the visitor's real address; port 80 redirects; an unknown host (or the bare IP) gets a 421. A stream from `/live/stories` held for 6½ minutes: the engine's pings every 20 s, and a story published by the 5-minute job, arrived as they were sent.
- **SSL Labs: A+** for `test2.miniscript.org` through front (A+ ignoring trust; no warnings), as M11 had for one app.
- **Isolation, as the real users under systemd: 27 checks, all passed**: each engine refused the other's data, config, code, state, dropbox, engine socket and writer socket, and its own code (writing) and dropbox (reading), and front's certificates; each could read its code and reach its own writer; front could read no partition and reach no writer. Five processes, five users (`ps`); the sockets as designed (`ls -l /run/fourfold/`).
- **Not seen on the server:** dropbox lines from app traffic, since neither sample app writes any; the container and end-to-end tests cover the writer.
- **Found deploying:** `deploy.sh` lost an empty `--memory` over ssh (fixed); a 421's reason phrase was "Unknown" (added).
